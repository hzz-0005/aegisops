# 请求级失败事件契约（Lab v1）

这个契约记录一次业务请求内由服务自身报告的失败事实，用于调查具体请求。它不把 Prometheus 聚合告警自动绑定到该请求，也不改变 Incident 分组、根因判断或修复授权。

## 写入与查询

- `POST /api/v1/request-events`：服务提交 `schema_version=1`、`source_event_id`、`service`、`trace_id`、`span_id`、`failure_code`、可选 `resource` 和带时区的 `occurred_at`。当前只接受已登记服务、最近 10 分钟至未来 30 秒的事件，以及符合格式的标识。写入令牌按服务配置，令牌只能上报对应 `service`；新增服务通过 `AEGISOPS_REQUEST_EVENT_SERVICE_TOKENS` 的映射配置，不必改授权代码。配置拒绝两个服务复用同一令牌。
- 相同服务和 `source_event_id` 重试返回原事件；相同键却改变事实返回 409。这保证投递重试不会产生另一条事实。
- `GET /api/v1/request-events/{event_id}` 与 `GET /api/v1/request-traces/{trace_id}/events` 使用开发操作员令牌。后者按发生时间和事件 ID 排序，最多返回前 50 条；空数组表示库中没有匹配事件，不证明请求没有故障。
- `GET /api/v1/request-events/{event_id}/verification` 向 Tempo 读取该 Trace，核对**相同服务的指定 Span ID**及其失败码、资源属性。`VERIFIED_SPAN_FACT` 只证明这条请求事实在追踪中存在；`SOURCE_ASSERTED` 只表示来源提交，尚未核对。Trace 尚未到达或 Tempo 不可用时保持不确定。

当前 Lab 的订单服务在支付依赖传输失败时提交 `dependency_transport`，网关在上游 5xx 时提交 `upstream_http_5xx`。两条事件可共享一次请求的 Trace ID，但这只能说明它们处在同一次请求链路，不能单凭这一点证明所有相关告警和 Incident 同根因。

## 人工附加到 Incident

`POST /api/v1/incidents/{incident_id}/request-evidence` 只接受开发操作员令牌、请求事件 UUID、预期 Incident 版本及非空理由。写入前重新从 Tempo 核对指定服务 Span 和失败事实；未达到 `VERIFIED_SPAN_FACT` 时返回 409，不创建关联。不存在的 Incident 或事件返回 404，版本变化返回 409。相同操作员与理由的重复提交返回同一记录；已有记录的理由不允许悄悄覆盖。`GET` 同路径用开发只读令牌列出记录。

记录带操作员、理由、附加时 Incident 版本、验证状态和时间线事件，关系状态固定为 `OPERATOR_SELECTED_CONTEXT`。附加证据**不提高 Incident 版本**，不重新运行 Agent，也不进入自动分组、根因分数、修复方案或执行器。它只是操作员选择的一条已核验请求事实，不能据此声称聚合告警属于该请求。事故工作台展示该区并提供手工填写事件 UUID 和理由的表单。当前身份仍是固定开发操作员，不能用于生产审计身份。

一次在线验收把同一 DNS 故障窗口的订单事件、网关事件分别附加到各自 Incident；两条记录均为 `VERIFIED_SPAN_FACT / OPERATOR_SELECTED_CONTEXT`，Incident 版本仍为 3，重复提交没有增加时间线。共享 Trace 没有自动给另一 Incident 增加记录或合并事故。

## 只读请求失败分组

`GET /api/v1/request-failure-cohorts?window_minutes=60&min_distinct_traces=2` 用已入库请求事件构成窗口内分组，键为精确的 `(service, failure_code, resource)`。响应逐条列出事件 ID、来源事件 ID、Trace ID、Span ID 和发生时间，并显示不同 Trace 数。可用 `service` 过滤；窗口限制为 1–60 分钟，门槛限制为 2–20 条不同 Trace。窗口内超过 1000 条事件时接口返回 409，要求缩小窗口，避免静默截断。

`membership_status=PERSISTED_EVENT_SET` 仅说明**返回成员是控制面实际保存的事件**，不说明投递零丢失，也不表示已核验每条 Span。`alert_binding_status=UNBOUND` 明确表示没有建立与 Prometheus 告警或 Incident 的直接来源关系。同服务、同错误码、同资源也可能有不同根因；这个分组不能自动并案、判根因或建议动作。

两次真实 DNS 故障探针后，在线分组得到订单和网关各 2 条事件、各 2 条不同 Trace；门槛设为 3 时为空。原始响应见 `eval/request-cohorts-20260930T090542Z.json`。这证明精确成员集的只读查询可用，尚未构成来源绑定告警。

## 固定窗口的已核验来源信号

`python -m scripts.materialize_request_signals --window-start 2026-09-30T08:50:00Z` 对已关闭的 UTC 10 分钟窗口运行一次监测。窗口结束至少 2 分钟后才可定稿。它只读取该窗口已入库事件，按精确 `(service, failure_code, resource)` 分组；每组须至少包含 2 条不同 Trace，且逐条向 Tempo 核对指定服务、Span ID、失败码和资源属性。单窗口最多 1000 条事件、单信号最多 64 个成员；超限或任一成员核验失败时拒绝**整个窗口**，不静默截断或降级核验。

信号持久保存监测规则版本、窗口、分组键、精确事件成员和每个成员的 `VERIFIED_SPAN_FACT` 核验结果。新写入的成员还保存核验记录时刻；迁移前已经核验的历史成员因没有精确核验时刻，该字段为空。所有候选组核验通过后，信号与**完整窗口事件 ID 快照**在同一数据库事务中提交；新窗口失败不会留下部分信号。相同窗口重复执行返回原信号 ID 与快照。定稿前成员变化会中止本次提交；定稿后到达、发生时间属于该窗口的事件作为迟到事件单独显示，不改写快照和信号。`GET /api/v1/request-failure-signals` 用开发只读令牌列出信号，`GET /api/v1/request-failure-signal-window?window_start=...` 返回快照、摘要、信号数及迟到事件 ID。

监测器已由独立 Compose 服务自动调度，也可手工触发；尚未设定生产保留策略。2 分钟是本机 Lab 的操作水位，不能保证业务事件零丢失或不存在更晚的投递；迟到统计在查询时由当前事件集与定稿快照求差。它只证明返回的请求成员确有对应的 Span 失败事实；缺失事件不能当作正常请求。相同症状可能来自不同根因，因此 `root_cause_status=UNDETERMINED`、`alert_binding_status=UNBOUND`；信号不进入 Prometheus Alert→Incident、自动并案或修复执行。

2026-09-30 的真实 DNS 样本在 `08:50–09:00 UTC` 窗口生成订单和网关各 1 条信号，每条各含 2 个已核验事件。重复运行得到相同信号 ID，未授权查询返回 401。原始报告为 `eval/request-signals-20260930T141453Z.json` 和重复报告 `...T141524Z.json`。

### 跨根因反例（2026-10-01）

在同一窗口并发注入**商品币种契约违例**与**支付目标 DNS 错误**，各执行 2 次独立请求。两者均使网关返回 502，且网关都上报 `upstream_http_5xx / order-service`；订单服务则分别上报 `business_contract_rejected / sku-demo-currency` 与 `dependency_transport / payment-service`。请求级 Trace 由实验脚本逐个指定，8 条事件全部入库并经 Tempo 核验。故障清除后两个商品均恢复 200。

监测器实际生成 3 条信号：网关信号的 4 个成员覆盖**两种不同注入根因**，两个订单信号各有 2 个成员且分别对应单一注入故障。原始样本 `eval/signal-collision-20261001T112758Z.json`，信号成员审计 `eval/signal-collision-audit-20261001T113204Z.json`。注入原因是实验已知真值，监测器本身没有从网关症状推断根因。

因此接口明确标记 `signal_kind=REQUEST_FAILURE_SYMPTOM`；同一个信号允许包含不同根因的请求，`root_cause_status=UNDETERMINED` 与 `alert_binding_status=UNBOUND` 必须保持。未来要做根因分组，应另用请求级上下游证据提出可审计的关系，并用这种跨根因样本检验；不能直接把当前信号映射为一个 Incident。该实验是一窗口的小样本反例，不是误报率或生产准确率估计。

`0021_signal_window_snapshot` 上线后，对该反例窗口定稿并重复运行：窗口快照为 8 个事件、3 条信号、迟到事件 0，摘要及完整事件 ID 见 `eval/request-signals-20261001T132435Z.json`；第二次运行没有新增信号，见 `...T132449Z.json`。查询代码对新增迟到事件的差集有定向测试；当时尚未做真实延迟投递，已于 2026-10-08 补齐，见下文在线报告。

### 自动调度与运行状态（2026-10-01）

独立的 `request-signal-detector` Compose 服务每 10 秒检查一次已过 2 分钟水位的固定窗口，单轮最多补登记 6 个窗口，防止重启后突然扫完整个历史。首次启动只从最近 6 个合格窗口开始；已有运行记录后按最新记录继续补齐长时间停机后的窗口。每个窗口的状态由 `0022_request_signal_runs` 保存为 `PENDING → RUNNING → FINALIZED`；失败时进入 `RETRYABLE`，最多尝试 5 次，退避 15、30、60、120 秒，随后 `BLOCKED`。事件数或单信号成员数超限直接阻塞。运行中进程退出后，租约到期再领取；同一窗口的原子定稿和重复执行保证不会增加第二份信号。

`GET /api/v1/request-failure-detector/runs?limit=12` 使用开发只读令牌返回最近窗口的尝试次数、状态、下一次重试、租约和错误**类别**，不保存原始异常正文。事故工作台展示最近 12 个窗口的定稿、重试和阻塞数量，以及最新窗口。监测器仍只形成 `REQUEST_FAILURE_SYMPTOM`；它不写 Prometheus Alert、Incident、审批或执行记录。首轮在线启动自动登记并定稿 6 个最近窗口，均一次成功；随后跨过下一个时间边界，`15:10 UTC` 窗口也自动一次定稿。7 条状态的原始报告为 `eval/request-detector-20261001T152330Z.json`。手机端 Edge 页面显示运行数量且 390px 无横向溢出，截图 `docs/screenshots/ops-detector-mobile.png`（拍摄时为 6 窗）。失败状态转换有定向测试；2026-10-08 已完成真实 Tempo 中断及同记录重试定稿，见下文。

## 来源与生产边界

### 真实来源事件延迟投递工具

`python -m scripts.evaluate_request_event_delay` 通过临时 Compose 覆盖，只把订单及网关的事件投递地址改到宿主机随机路径中转器；不改业务 Span 或事件构造代码。中转器仅在内存保存原始 JSON 及原始认证头，认证头不写报告。使用两个真实失败请求，接近窗口结束时捕获 4 条事件，确认控制面尚无这些事件；自动监测器持续运行，在窗口水位后先定稿。随后将原始事件通过正常 HTTP 写入接口转发，检查迟到事件 ID 集合、完整 Span 核验和不可变窗口快照。

这是测试用的暂存传输，不提供生产持久队列保证；接收成功只表示进入当前中转进程内存。脚本退出恢复两个业务容器的原投递配置，关闭中转器并删除临时 Compose 覆盖；报告保存来源事实而不保存认证凭据。运行会重新创建订单和网关容器，故障开关有恢复逻辑及 TTL。最多等待一个窗口及水位。该试验通过后，仍需根据生产需求决定持久队列、死信处理及补偿调查策略。

在线报告 `eval/request-event-delay-20261008T052715Z.json`：自动监测先定稿 05:20–05:30 UTC 空窗口，随后通过普通写入接口投递原始事件。4 条全部列为迟到事件、4/4 通过 Tempo 精确核验，原来源 ID 保持一致；快照摘要和信号结果不变，重复定稿仍返回空信号。业务服务原投递配置已恢复。迟到事件可见不意味着会补发告警；当前空快照仍有 0 条信号，发现率评估必须计入该局限，未来补偿处理应单独留痕。

### 调度恢复验收（2026-10-08）

恢复时发现约 190 个已登记待处理窗口，原调度每 10 秒只处理一窗。现改为每批最多 6 窗，满批后隔 1 秒继续，未满批或发生轮询异常则隔 10 秒检查；仍沿用原有租约、退避和尝试上限。工作台展示最近 12 窗的待处理、处理中、定稿、重试和阻塞数，状态使用中文；这不是全量积压总数。

`python scripts/audit_request_detector.py` 只读检查从首个登记窗口至当前水位的连续性、未完成窗口和定稿快照，输出 `eval/` 报告。空窗口通过只能证明调度正常，不能证明故障识别准确。

`python scripts/evaluate_detector_recovery.py` 在随机独立测试租户内使用真实 PostgreSQL，验证活动租约排他、到期接管、旧尝试成功及失败写入被拒绝、重试退避、相同运行记录重领、定稿不重领、超限窗口阻塞，以及模拟迟到事件可见且不改写快照，共 10 项。测试结束清理该租户的临时记录。租约与退避使用传入时间推进，迟到样本直接入库；不代表真实进程崩溃、HTTP 延迟投递或 Tempo 故障在线验收。

本次常规镜像构建被 PyPI TLS 连接失败中断，在线监测器通过已有依赖镜像仅覆盖入口代码完成部署；没有改变依赖或关闭 TLS 校验。后续网络恢复时可按标准 Dockerfile 完整重建。

### 非空窗口的 Tempo 故障验收工具

`python -m scripts.evaluate_detector_tempo_outage` 仅用于本机开发 Lab。它暂停自动监测容器，用两次真实 DNS 失败请求产生订单及网关来源事件，恢复业务故障后等待真实窗口水位。随后短暂停止 Tempo，调用与监测容器相同的调度应用逻辑，检查运行进入 `RETRYABLE`、窗口及信号零部分写入；启动 Tempo 后等待实际退避时间，要求同一运行记录第二次尝试定稿，全部实际请求成员通过 Span 核验。最后恢复自动监测容器，保存成功或失败报告。

脚本最多等待一个 10 分钟窗口加 2 分钟水位；这期间自动监测暂停，业务服务持续运行。退出清理会恢复已暂停的容器，DNS 故障开关也有独立恢复逻辑及 90 秒 TTL。手动终止解释器或宿主机故障仍需检查容器状态。该验收证明真实 Tempo 读取故障的应用调度重试路径，不代表真实监测进程在执行中崩溃或事件持久投递能力。

2026-10-08 在线验收：首次核验失败后无快照和信号；恢复后同一运行记录第二次定稿。4 条来源事件完整保存，只有网关同症状的 2 条请求符合门槛；两次订单失败分别为超时和连接错误，各只有一个 Trace。最初脚本把全部请求误认为应进入信号，断言失败；原报告保留在 `eval/detector-tempo-outage-20261008T051616Z.json`。修正期望语义后，使用 `--audit-report` 原报告路径重新检查已有事实，无重复注入，最终通过报告 `eval/detector-tempo-audit-20261008T052401Z.json`。重复定稿的信号 ID 和摘要相同。场景标签只作注入真值，不能替代实际成员分组规则。

事件由业务服务在请求 Span 内标记，再由响应中间件在返回响应后短超时投递。投递是尽力而为：控制面不可用、进程退出或超时可能丢失事件；数据库中没有事件不能当作阴性证据。当前静态令牌和开发租户只适用于本机 Lab。

按服务令牌只限制谁可以声称某个服务；它不是生产级服务身份，也不能证明某条 Prometheus 聚合告警由这些请求事件产生。2026-09-30 的部署测试中，订单写入入口拒绝网关令牌和旧共享令牌；真实 DNS 故障重放仍得到订单、网关各一条 `VERIFIED_SPAN_FACT` 事件，报告为 `eval/request-events-20260930T085724Z.json`。

未来接生产业务时，接入器需要服务身份、持久投递队列、重试及死信处理、租户隔离与保留期。若要把聚合告警关联到请求事件，必须提供可审计的直接来源绑定，或者经反例验证的依赖和时间因果证据；人工确认应记录理由。宽时间窗 Trace 交集只可作为调查上下文，不可驱动自动合并或动作。

在线样本：`eval/request-events-20260929T133607Z.json` 中，同一请求的订单和网关两条事件均通过指定 Span 的事实核验。该样本证明两条请求事实成立，不证明聚合事故的分组正确。

### 容量阻塞与有审计重排（2026-10-08）

真实连续负载产生 26 个同症状成员，原 20 上限拒绝了整个窗口。现上限为每信号 64 成员、每窗口 1000 事件，仍完整核验、不采样、不截断；超限继续阻塞。实际原窗口 45 个事件，以 8/11/26 成员形成 3 条信号。上限调整是 Lab 操作容量变化，不改变症状分组语义或证明生产容量。

迁移 `0023_detector_requeue_history` 保存阻塞重排历史。仅开发环境可用 `python -m scripts.requeue_request_detector` 对指定 BLOCKED 记录操作；必须提交预期 generation、操作员和理由。锁定记录后保存旧状态/错误/尝试数，增加代次并重置当前尝试，旧代即使尝试序号相同也不能提交完成。已定稿窗口不能重排，原快照不可变。审计同时区分当前代尝试与跨代累计尝试，不能用重置掩盖失败。

### 调查中的依赖请求上下文（2026-10-08）

订单库存与支付调用都可上报实际超时/传输/HTTP5xx失败的请求Span事实。调查工具按租户、服务、已登记依赖、固定失败码以及告警发生时间±30秒取最多4个来源候选，逐条核对Tempo服务、精确Span、失败码和资源。只有VERIFIED_SPAN_FACT作为VERIFIED_DEPENDENCY_REQUEST进入持久调查报告，仍CONTEXT/UNBOUND。具体请求事实成立不证明它与时间邻近的聚合告警直接相关，也不直接更新Incident分组或修复计划；无候选或核验不可用不是正常证据。

运行时状态由Lab执行器已有Docker访问独立采集，调查通过Prometheus读取鲜活历史状态，作为另一个上下文。源检查失败或观测超过15秒不复用旧状态；running不是健康保证，paused不是全部事故根因证明。详见[运行时与请求验收](runtime-requests-2026-10-08.md)。

### 请求上下游关系（2026-10-08）

调查可按租户、服务与±30秒读取最近4条任意失败码事件，再核验精确Span事实、父路径、服务边界、两端5xx与时序。每Trace最多16事件/256Span、路径最多16层，时间偏差最多1毫秒；缺失、混合、重复或歧义拒绝关系。VERIFIED_REQUEST_FAILURE_LINK记录事件对和路径，仍CONTEXT/UNBOUND/UNDETERMINED，不自动合并或授权动作。有限候选不代表全量请求覆盖；异步和多失败链路尚未覆盖。详见[请求关系验收](request-links-2026-10-08.md)。

### 入站失败与数据库读取事实（2026-10-11）

库存来源使用独立服务令牌，Compose 与 `.env.example` 的服务令牌映射包含 `inventory-service`。库存读取可提交 `database_lock_timeout`、`database_query_cancelled` 或 `database_error`，字段格式仍为 schema v1。采集仅保存固定读取操作、SQLSTATE、超时配置与耗时，不提交 SQL、参数或连接串。

入站查询使用同租户目录依赖选择调用方，不只查询告警服务自身发出的请求。数据库查询在±30秒范围内最多检查8个候选、保存4条已核验事实；优先存在同Trace调用方来源的候选，这只是检索线索。`VERIFIED_DATABASE_OPERATION` 要核验精确服务、Trace/Span、事实、时间范围、错误状态和数据库属性，`55P03` 锁等待超时与 `57014` 查询取消保持区别。

数据库事实中的 `caller_links` 必须另外核验父路径、唯一服务边界、两端5xx及发生顺序；`dependency_http_5xx` 可作为调用方边界，纯超时没有错误响应时不建立此关系。事实和调用关系保持CONTEXT/UNBOUND，当前状态UNKNOWN、根因UNDETERMINED，不自动合并聚合事故或授权终止会话。候选预算不保证全请求覆盖。实际验收与局限见[数据库调用路径记录](database-ancestry-2026-10-11.md)。
